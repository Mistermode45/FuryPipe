# FuryScore V1

## Purpose

FuryScore ranks capability candidates for a specific task without granting runtime authority.

It combines:

- task relevance;
- a real in-process FuryTrust report;
- reviewed provenance;
- declared health;
- maintenance state;
- optional qualified performance evidence;
- FuryTrust risk penalty.

It deliberately does **not** use GitHub stars, downloads, followers, marketplace rank, or other popularity signals as a quality score.

## Core rule

```text
score != trust
score != permission
score != execution authorization
```

Every FuryScore result returns:

```text
executionAuthorized: false
```

Actual execution remains governed by Capability Router, host inventory, plugin/MCP permissions, FuryTrust policy, Agent Runtime, and any required approvals.

## Routing states

### RANKED

The candidate may participate in normal ranking.

This still does not authorize execution.

### REVIEW_REQUIRED

The underlying FuryTrust verdict is `RESTRICTED`.

The candidate can be compared, but a human/policy approval boundary remains.

### REFERENCE_ONLY

The integration decision is `REFERENCE_ONLY`.

The candidate can inform research or implementation without being promoted to an executable integration.

### BLOCKED

Used for:

- FuryTrust `BLOCKED`;
- FuryTrust `QUARANTINED`;
- FuryTrust `UNKNOWN`;
- integration decision `REJECT`.

A very high relevance score cannot override this state.

## Score composition

V1 uses a bounded 0..100 score.

Maximum positive contributions:

| Component | Max |
|---|---:|
| task relevance | 40 |
| FuryTrust verdict | 20 |
| provenance | 10 |
| health | 8 |
| maintenance | 7 |
| qualified performance | 15 |

FuryTrust risk contributes a penalty of up to 20 points.

The formula is intentionally inspectable and versioned as:

```text
furyscore-v1
```

Changing the weighting policy requires a new policy version.

## Relevance

Relevance is caller-supplied on a 0..1 scale.

FuryScore does not infer semantic relevance itself.

The intended architecture is:

```text
Task
  ↓
Capability Router / semantic analyzer
  ↓
relevance candidates
  ↓
FuryTrust
  ↓
FuryScore
  ↓
ranked recommendations
```

This keeps semantic task matching separate from trust and performance evidence.

## FuryTrust requirement

FuryScore accepts only reports generated by the current in-process FuryTrust evaluator.

A structurally similar object is rejected.

This prevents callers from creating a JSON object that merely claims:

```text
verdict: TRUSTED
```

and receiving trust credit.

The report candidate ID must exactly match the capability candidate ID.

## Performance evidence

Performance bonuses require a qualified evidence object produced by:

```text
qualifyFuryCapabilityPerformance()
```

Qualification is fail-closed.

Required:

- exact candidate ID;
- benchmark artifact SHA-256;
- exact provider;
- exact model;
- exact workload ID;
- at least 5 samples;
- no quality regression;
- passing exactness;
- zero benchmark errors.

The evidence is bound to the exact provider/model/workload supplied to the scoring request.

Evidence for:

```text
openai / gpt-5.6-sol / marketing-website
```

cannot be reused for:

```text
anthropic / another-model / minecraft-plugin
```

without a separate qualified evidence record.

## Performance weighting

Qualified performance begins with a bounded evidence credit and can gain additional points for:

- measured quality improvement;
- lower token usage;
- lower latency;
- lower cost.

Token, latency, or cost regressions can reduce the performance component.

Quality regression, exactness failure, insufficient samples, or benchmark errors prevent qualification entirely.

## Popularity

The following metadata is deliberately excluded from the score:

- stars;
- downloads;
- dependents;
- social engagement;
- marketplace position.

These values may be useful discovery signals, but they do not establish:

- correctness;
- security;
- maintenance quality;
- task suitability;
- performance;
- reliability.

FuryPipe should not choose a worse capability merely because it is more popular.

## Provenance

Provenance contributes only when it has been reviewed.

Unreviewed provenance receives a strict cap even if the candidate self-declares itself as official or first-party.

The current ordering is conservative:

```text
FIRST_PARTY
OFFICIAL
VERIFIED_COMMUNITY
COMMUNITY
FORK
MIRROR
UNKNOWN
```

This is only one score component. It never bypasses FuryTrust.

## Health and maintenance

Health and maintenance are independent.

Examples:

- an actively maintained project may still have unknown runtime health;
- a healthy currently running MCP can belong to a repository in maintenance mode;
- archived or unhealthy capabilities lose ranking points but are not silently rewritten into a security verdict.

## Determinism

For the same:

- candidate;
- generated FuryTrust report;
- relevance;
- provider/model/workload;
- qualified performance evidence;

FuryScore produces the same score and stable ordering.

Ranking tie-breakers are:

1. routing state;
2. higher score;
3. lower FuryTrust risk score;
4. lexical candidate ID.

## Current limitations

FuryScore V1 does not yet:

- invoke capabilities;
- automatically pull benchmark files from GitHub;
- authenticate benchmark publishers;
- calculate statistical significance;
- compare model-family-wide performance;
- infer task relevance;
- replace FuryTrust;
- replace FuryBench;
- choose provider credentials;
- modify Capability Router automatically.

Those integrations should be added only after the V1 ranking/evidence contract is stable and verified.
