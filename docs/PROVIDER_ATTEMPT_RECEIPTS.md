# FuryPipe Provider Attempt Plan Receipts

## Purpose

A Provider Attempt Plan Receipt is a compact, plaintext-free audit record for
one `FuryProviderAttemptPlan`.

It records which exact provider/model/workload scope was planned, which model
adapter and Context Optimizer profile states were observed, and the digest of
the resulting attempt-specific FuryPrompt.

The receipt does not execute anything.

## Boundary

The receipt is created from a planning-only object:

```text
FuryProviderAttemptPlan
        ↓
structural validation
        ↓
FuryPrompt canonical compilation
        ↓
digests + bounded metadata only
        ↓
Provider Attempt Plan Receipt
```

It does not:

- call a provider;
- run Context Optimizer;
- execute a tool, MCP method, skill, or subagent;
- authorize execution;
- persist prompt plaintext;
- prove the input object was produced by the official planner;
- prove a provider accepted or executed a request;
- verify a current context-runtime result.

## Plaintext-free output

The receipt does not copy FuryPrompt section contents.

Instead it records:

- FuryPrompt `promptDigest`;
- FuryPrompt source digest;
- exact FuryPrompt compile-input digest;
- rendered prompt byte count;
- FuryPrompt level.

Adapter additions and task text therefore remain absent from the JSON receipt.

The input prompt is compiled locally in memory only to reuse FuryPrompt's
canonical validation and digest contract.

## Exact scope

Every receipt binds to:

```text
providerId
model
workloadId
```

The creator verifies that the top-level attempt scope exactly matches both:

- the Provider Attempt Adapter Plan;
- the Context Optimizer Profile Plan.

A mismatch fails closed.

There is no provider-family, model-family, prefix, or fuzzy workload matching.

## Adapter evidence

The receipt records:

- adapter state: `IDENTITY`, `APPLIED`, or `BLOCKED`;
- adapter evidence: `none` or `verified`;
- adapter ID and SHA-256 digest only when applied;
- bounded block reason codes.

An `APPLIED` state must carry an ID, SHA-256 digest, and verified evidence.

`IDENTITY` and `BLOCKED` must not expose an applied adapter ID/digest.

A `BLOCKED` state must contain at least one substantive blocker.

## Context profile evidence

The receipt records:

- context-profile state: `IDENTITY`, `QUALIFIED`, or `BLOCKED`;
- evidence state;
- profile ID and SHA-256 digest only when qualified;
- bounded block reason codes.

A `QUALIFIED` state must include profile ID, profile digest, options, and
verified evidence in the source plan.

The receipt deliberately does not serialize the optimizer options themselves.
The profile digest is the stable identity for the qualified profile definition.

## Prompt consistency

The top-level `plan.prompt` and `plan.adapter.prompt` must compile to the same
FuryPrompt prompt digest and source digest, and must also have the same
canonical compile-input digest.

The compile-input digest binds section values plus compile metadata such as
explicit level, `securityCritical`, and `exactGuardMode`. This closes cases
where two inputs could render the same text while carrying different compile
semantics.

If any of these identities differ, receipt creation fails closed.

This prevents an audit receipt from silently describing one prompt while the
attempt plan carries another.

## Non-execution invariants

The receipt creator accepts only planning-only plans.

All of the following must remain false:

```text
networkCallExecuted
providerRequestExecuted
optimizerExecuted
executionAuthorized
```

The nested adapter and context-profile planning flags are also validated.

A forged plan that claims execution or authorization is rejected.

## Verification semantics

The receipt contains intentionally narrow verification fields:

```text
structuralConsistency = verified
plannerProvenance     = not-verified
providerResult        = not-executed
currentContextResult  = not-verified
```

These terms are not interchangeable.

### structuralConsistency = verified

The supplied object passed this module's structural invariants and canonical
FuryPrompt digest checks.

It does **not** prove where that object originated.

### plannerProvenance = not-verified

The current Provider Attempt Planner does not attach an unforgeable provenance
marker or signed receipt to each plan.

Therefore this receipt must not claim that an arbitrary structurally valid
object was definitely generated by the official planner.

### providerResult = not-executed

No provider request is performed by this receipt layer.

### currentContextResult = not-verified

A benchmark-qualified context profile is historical evidence about a measured
profile. It is not verification of a future/current context inventory result.

## Receipt digest

Each receipt includes a SHA-256 digest over its canonical JSON fields excluding
the digest field itself.

For the same plan, receipt generation is deterministic.

Changing the exact scope, prompt digest, adapter state, context-profile state,
or blocker metadata changes the receipt digest.

## Verification helper

`verifyProviderAttemptPlanReceipt(receipt, plan)` recomputes the expected
receipt from the supplied plan and requires exact JSON equality plus receipt
digest equality.

This verifies:

```text
receipt matches this supplied plan
```

It does not verify:

```text
supplied plan came from trusted runtime provenance
```

That distinction is intentional.

## Relationship to the Provider Attempt Context Runtime

The future Provider Attempt Context Runtime will run Context Optimizer and
produce a new attempt-specific prompt with injected context.

This V1 receipt describes the **planning stage before that runtime execution**.

A later runtime receipt should be a separate format and must distinguish:

- planning evidence;
- benchmark profile qualification;
- actual Context Optimizer execution;
- current context plan;
- final injected prompt digest;
- provider execution state.

Do not overload this planning receipt to claim those later events occurred.

## Current limitations

V1 does not provide:

- signed provenance;
- persistent qualification attestation;
- provider response receipts;
- Context Optimizer runtime receipts;
- remote timestamp authority;
- statistical benchmark claims;
- release or deployment evidence.

Those remain separate future contracts.
